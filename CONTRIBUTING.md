# Contributing to rer-dsp-job-data-migration

Thank you for your interest in contributing to the DSP data migration job.

This repository is the ETL module of the **DSP (Data Sharing Platform)**, part
of the Rural Environmental Registry (RER). It copies geospatial data from the
adopter source database into the DSP databases.

Please read the [Code of Conduct](CODE_OF_CONDUCT.md) before participating.

Full project documentation lives in
[dsp-docs](https://github.com/Rural-Environmental-Registry/dsp-docs).
The guide below covers this module only.

---

## What belongs here

Changes to the migration job belong in this repository:

- Spring Batch jobs under `br.car.dsp_batch` (territories, area of interest, extra layers, KPI calculation, watermark)
- Tests under `src/test/java`
- Job operational configuration in `config/application/application.yaml` (generated by dsp-core `./config.sh`)
- This module's `README.md`

The job reads the source database and does not change it. It writes a light
copy to `target` (`dsp-db`) and full geometries to `geo-target`
(`dsp-geoserver-db`). After a successful run it flags territories that need a
new download file. It does not publish GeoServer layers and it does not
generate those files.

Other DSP work belongs in its own repository:

| Change | Repository |
|--------|------------|
| Architecture, installation, and platform guides | [dsp-docs](https://github.com/Rural-Environmental-Registry/dsp-docs) |
| REST API | [dsp-backend](https://github.com/Rural-Environmental-Registry/dsp-backend) |
| Web interface | [dsp-frontend](https://github.com/Rural-Environmental-Registry/dsp-frontend) |
| Stack orchestration, gateway, and adopter configuration | [dsp-core](https://github.com/Rural-Environmental-Registry/dsp-core) |
| Pre-generated download files | [dsp-job-geo-file-generation](https://github.com/Rural-Environmental-Registry/dsp-job-geo-file-generation) |

Source tables, hierarchy, and KPI themes come from YAML generated by
`dsp-core` (`./config.sh`). Do not hardcode adopter-specific tables in Java.
When the job runs is defined by `./setup.sh`, not by this repository.

## How to contribute

### 1. Bugs and features

1. Open an issue describing the problem or the change in the dsp-core repository:
   https://github.com/Rural-Environmental-Registry/dsp-core/issues
2. Fork the repository
3. Create a branch from `develop`: `git checkout -b feat/short-description`
4. Make the change
5. Run the tests: `./mvnw test`
6. Commit with a clear message
7. Open a pull request against `develop`

### 2. Job changes

Keep each step in the package that already owns it:

| Area | Package |
|------|---------|
| Territory levels | `br.car.dsp_batch.batch` |
| Area of interest | `br.car.dsp_batch.aoi` |
| Extra layers | `br.car.dsp_batch.layer` |
| KPI calculation | `br.car.dsp_batch.kpi` |
| Incremental copy (watermark) | `br.car.dsp_batch.sync` |
| Download-file flags | `br.car.dsp_batch.geofile` |

Copy order stays level 1, level 2, level 3, area of interest, extra layers,
then KPI calculation. Cover the change with a test in `src/test/java`.

### 3. Documentation of this module

Keep `README.md` limited to this module: purpose, stack, and how to run it.
Platform-wide guides (architecture, quick start, full installation) go to
[dsp-docs](https://github.com/Rural-Environmental-Registry/dsp-docs), in both
`docs/pt-br/` and `docs/en/`.

## Local setup

Requirements: Java 21 and the Maven wrapper already in the repository
(`./mvnw`).

Run the job:

```bash
./mvnw spring-boot:run
```

The preferred way to run a real migration (source database, both DSP databases,
and schedule) is `./setup.sh` in
[dsp-core](https://github.com/Rural-Environmental-Registry/dsp-core).

Run the tests:

```bash
./mvnw test
```

The JaCoCo report is written by `./mvnw verify` to
`target/site/jacoco/index.html`.

## Code standards

- Java 21, Spring Boot 3.4.2, Spring Batch, Maven, PostgreSQL/PostGIS
- Artifact id: `dsp-batch`
- Source encoding is UTF-8
- Package root: `br.car.dsp_batch`
- Connections stay `source`, `target`, `geo-target`, and `batch` (schema `data_migration`)
- Spring Batch schema initialization stays `never` (`spring.batch.jdbc.initialize-schema`)
- The source datasource is read-only from this job's point of view
- `target` stores business data and a geo summary. Full geometries go to `geo-target` only

## Review process

1. **Tests** — `./mvnw test` must pass
2. **Peer review** — at least one maintainer reviews the pull request
3. **Merge** — approved pull requests are merged into `develop`

---

## Commit message format

Use conventional commits:

```
feat: flag level 3 territories after a successful migration
fix: keep the watermark when the job fails
test: cover KPI area written only to the light database
docs: describe local spring-boot:run in the module README
```

**Types:**

- `feat:` — new behavior
- `fix:` — bug fix
- `test:` — tests only
- `docs:` — documentation only
- `refactor:` — internal change with the same behavior
